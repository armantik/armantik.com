Design a Chat System Like WhatsApp

Chat introduces stateful servers: millions of open connections that must find each other. The design turns on how a message travels from one socket to another, and what happens when the other side is offline.

By Arman Ajabkhani, Senior Backend Engineer · Updated 31 Oct 2026

The short answer

Requirements. One to one chats and groups of up to 100, delivery and read receipts, online status, push notifications for offline users and history on every device; delivery is fast, messages keep their order within a conversation, and an acknowledged message is never lost.

The design. Each client keeps one WebSocket open to a stateful chat server, while login, profiles and media stay on ordinary HTTP services. A message gets a time sortable Snowflake ID, is written to a wide column store partitioned by conversation before anyone is told, and then goes to the recipient’s inbox queue, which their chat server consumes and pushes down the socket. Offline users get a push notification, and every device catches up by asking for all messages after the last ID it has seen.

Interview prompt

Design a chat app like WhatsApp or Messenger: one to one and small group chats, online status, and sync across devices.

Requirements and estimates

Functional requirements

  • One to one and group chats of up to 100 members.
  • Delivery and read receipts, online presence.
  • Offline users get push notifications and catch up on reconnect.
  • History syncs across a user’s devices.

Non-functional requirements

  • Low delivery latency.
  • Messages ordered within a conversation.
  • Durable: an acknowledged message is never lost.

Estimates

WebSockets, long polling or short polling

TechniqueHow it worksTradeoff
Short pollingClient asks “anything new?” every few secondsSimple, but most responses are empty and waste capacity
Long pollingServer holds the request open until a message arrives or a timeoutFewer empty replies; still one request per message and constant reconnects
WebSocket PickOne persistent, two way connection over TCPReal time both ways; servers become stateful and need reconnect handling

Use WebSockets for messages only. Login, profiles, group management and media uploads stay on ordinary stateless HTTP services behind a load balancer.

Message order with Snowflake IDs

Client clocks drift, so ordering comes from IDs the server assigns. A Snowflake ID packs a timestamp into the high bits, so sorting by ID sorts by time, and each generator can mint thousands of IDs per millisecond with no coordination.

Message storage, presence and group chats

Message store

Chat is write heavy and reads are mostly recent. A wide column store (Cassandra, HBase, ScyllaDB) partitioned by conversation_id and sorted by message_id serves “latest 50 messages” from one partition. Discord runs this model on ScyllaDB, and Facebook Messenger ran it on HBase for years.

Multi-device sync

Each device keeps a cursor: the largest message ID it has. On reconnect it asks for everything after that ID, which also covers offline delivery.

Presence

Clients send a heartbeat every 5 seconds. A user is marked offline only after 30 seconds of silence, so a train through a tunnel does not flicker their status. Changes are published to friends over pub/sub; in large groups, presence is fetched only when someone opens the member list.

Groups

Small groups copy each message into every member’s inbox queue. Large channels store once and let members pull, like celebrities in the news feed.

What the interviewer probes next

A chat server crashes. What happens to its users?

Their sockets drop, and clients reconnect with backoff and jitter; service discovery (ZooKeeper, etcd) hands them another server. Messages were persisted before delivery, and clients resend anything unacknowledged with the same client message ID, which the server deduplicates.

Two people in a group send at the same moment. Who comes first?

Whoever the server assigns the lower ID. Using one ID source per conversation gives every member the same order; device timestamps are only for display.

How does end to end encryption change the design?

Keys live only on devices (the Signal protocol), so servers store and forward ciphertext. Server side search and message previews in push notifications no longer work unless the device decrypts them locally.

How do you deploy without dropping 10M connections?

Drain servers one at a time: stop accepting new sockets, ask connected clients to reconnect gradually, then restart. The load balancer must support long lived connections and not cut them on a fixed timeout.
