Design a URL Shortener Like TinyURL

The classic warm up. A small surface area that still tests estimation, ID generation, caching and the difference between a 301 and a 302.

By Arman Ajabkhani, Senior Backend Engineer · Updated 31 Oct 2026

The short answer

Requirements. Create a short link for a long URL, with an optional alias and expiry; send every visit on to the long URL in a few milliseconds; stay up, because a dead link breaks someone else’s page; never reuse a code.

The design. Stateless web servers behind a load balancer take a unique ID from a range they lease in blocks of 1,000, write it in base62 as a 7 character code, and store code and long URL in one table keyed by the code. A redirect reads the code from a Redis cache first, falls back to the store only on a miss, and answers 302 so every click passes through and can be counted. Click events go to a queue so redirects never wait for analytics, and the store is replicated for availability, not sharded, until the numbers demand it.

Interview prompt

Design a service like TinyURL: given a long URL, return a short one that redirects to it.

Requirements and estimates

Functional requirements

  • Create a short URL for a long one, with optional custom alias and expiry.
  • Visiting the short URL redirects to the long one.
  • Optional: click counts per link.

Non-functional requirements

  • Redirects are fast, a few milliseconds at the server.
  • Highly available: a dead short link is a broken page on someone else’s site.
  • Codes are never reused and are hard to enumerate.

    The point of these numbers is that modern machines are huge. Rules like “split the database at 100 GB” are long outdated, and sharding before the numbers demand it is a common interview mistake. At 500 GB, a URL shortener fits comfortably on one Postgres server; replicate it for availability, and shard only when throughput or size truly requires it.

    301 or 302 redirect for a URL shortener

    A 301 Moved Permanently is cached by the browser, so repeat visits never reach you. Less load, but you lose click analytics and cannot change or expire the link for that visitor. A 302 Found sends every click through your servers: more load, complete analytics. Most commercial shorteners use 302 because analytics is the product.

    Scaling redirects with a cache and the CDN

    Redirects outnumber writes 100 to 1, and clicks concentrate on recent and viral links. Cache code → long URL in Redis with LRU eviction. If the hottest 20% of a month’s links take most of the clicks, that is 20M × 500 B = 10 GB, which fits in one Redis node. Add read replicas behind the cache, and for extreme traffic answer redirects at the CDN edge.

    What the interviewer probes next

    How do custom aliases work?

    Same table, same unique key. Check availability on create and reserve words like api and login. To keep aliases from colliding with generated codes, generated codes are always exactly 7 characters and aliases must be another length, or both go through the same uniqueness check.

    How do expired links get cleaned up?

    Lazily on read (return 410 Gone when expired) plus a low priority job that deletes expired rows in batches. Never recycle codes: an old link printed in a book would suddenly point at a stranger’s page.

    How do you count clicks without slowing redirects?

    Redirect first, then publish a click event to a queue such as Kafka. Stream processors aggregate counts per link per minute into an analytics store. The redirect never waits on analytics.

    How do you stop abuse?

    Rate limit creation per user and IP, check new URLs against malware and phishing lists such as Google Safe Browsing, and require an account for high volume.
