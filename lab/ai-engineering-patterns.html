AI Engineering Patterns

A field guide for backend engineers: which pattern to reach for, what each one costs you, and how they combine in a real coding pipeline.

Field guide20 Sep 20269 min read

The golden rule

Use the simplest pattern that solves the problem. Patterns stack in layers of increasing complexity and cost. Each step up adds capability, and also latency, cost and new ways to fail.

1. Prompting patterns

The cheapest layer. Exhaust these before you add infrastructure.

PatternWhen to use
Zero-shotThe task is common and well defined ("summarize this")
Few-shotOutput format or style matters: show 2 to 5 examples
Chain of thoughtReasoning tasks: math, logic, multi-step analysis
Structured outputCode consumes the result: force JSON with tool use or JSON mode
Role or system promptA consistent persona, tone or set of constraints across a session

2. RAG patterns

Use RAG when the model needs knowledge it doesn't have: private documents, fresh data, large corpora.

PatternWhen to use
Naive RAGEmbed → retrieve top k → put into the prompt. Fine for small, clean corpora
Hybrid searchVector and keyword (BM25) together. When exact terms matter: IDs, names, code
RerankingRetrieve 50, rerank to 5 with a cross-encoder. Fixes poor precision
Query rewriting, HyDERewrite the question before retrieval. For vague or conversational queries
Semantic chunkingStructural or semantic chunks beat fixed-size chunks almost always
Agentic RAGThe model decides whether and what to retrieve, possibly in rounds. For complex questions across sources

3. Workflow patterns

Fixed control flow with an LLM inside each step. Predictable and debuggable, so prefer these over agents whenever the steps are known.

PatternShapeWhen to use
Prompt chainingStep 1 output feeds step 2A known sequence: outline → draft → edit
RoutingA classifier sends input to a specialised prompt or modelSupport triage; cheap versus expensive model routing
Parallelization (fan-out)Split → N parallel calls → aggregateIndependent subtasks, voting, per-document processing
Evaluator-optimizerGenerator and critic loop until acceptedQuality-critical output: code review, translation
Orchestrator-workersA lead LLM decomposes and delegatesSubtasks you can't predict upfront, with one point of control

4. Agentic patterns

The LLM controls the loop. Use them only when the path can't be decided in advance.

PatternWhen to use
Tool use, function callingThe foundation: the model picks tools and arguments
ReAct loopReason → act → observe → repeat. The default agent loop
ReflectionThe agent reviews its own output and retries. Better quality at a latency cost
PlanningWrite a plan first, then execute. For long multi-step tasks
MemoryShort term (the conversation) and long term (facts, preferences). When sessions must build on each other
Human in the loopApproval gates before irreversible actions such as payments, emails and deletes. Required for high-stakes tools

5. Agent collaboration patterns

"Multi-agent" is the umbrella term; the patterns below are specific shapes under it. Start with orchestrator-workers, the sensible default.

Orchestrator-workers (supervisor)A lead agent delegates; workers never talk to each otherUnpredictable subtasks, one point of controlThe supervisor's context grows with every result
Sequential pipelineA → B → C, each owns a stageKnown ordered stages, each with its own tools or contextErrors compound downstream
Evaluator-optimizerGenerator and critic loopQuality over latency, when "good" can be written down2 to 5× cost; the critic needs a rubric, not "is this good?"

HierarchicalSupervisors managing supervisorsGenuinely large scopes, which are rareFailure modes multiply; hard to trace

Fan-out, supervisor and swarm compared

Fan-out is a concurrency pattern rather than collaboration: workers never interact and can be plain prompt calls. Swarm is decentralised: routing logic lives inside each agent, and a handoff transfers the whole conversation.

Fan-outSupervisorSwarm
Who decides routingYou, in codeA central agentEach agent, locally
Workers runIn parallelParallel or sequentialOne at a time
Workers talk to each otherNeverNever (only via the supervisor)Directly, via handoff
Control returns to a centerYes (reduce step)Yes (supervisor)No, control wanders
DeterminismHighMediumLow
DebuggabilityEasyMediumHard

How agents communicate

This is a separate choice from the topology above.

  • Handoff: full control transfer; the receiving agent gets the conversation (OpenAI Agents SDK style).
  • Tool call: a sub-agent is invoked as a function and returns a result, which keeps the parent context clean (Claude and LangGraph subagent style).
  • Shared state: a graph state object or scratchpad that all agents read and write (LangGraph's core model).
  • Message passing: async messages or events between agents (AutoGen style, MCP-based systems).

The deciding factor is often isolation versus continuity. Supervisor sub-agents keep contexts isolated: the worker returns a conclusion and the parent stays clean. Swarm handoffs share the conversation history.

6. Case study: a ticket to PR coding pipeline

The shape that works is a sequential pipeline with fan-out inside the read-only stages and an evaluator loop at the end. Not a swarm, and not a free-form supervisor.

  1. Ticket
  2. ↓
  3. Investigate fan-out, read-only
  4. ↓
  5. Plan
  6. ↓
  7. Human approves the plan
  8. ↓
  9. Implement a single agent
  10. ↓ ↑ findings loop back, at most 2 or 3 rounds
  11. Verify fresh evaluator agents
  12. ↓
  13. PR description
  14. ↓
  15. Human merges

Investigate with fan-out, read-only sub-agents. This stage is search-heavy and fills context quickly. One agent traces the bug area, one maps the affected tests, one checks conventions and related PRs. Each returns a conclusion instead of file dumps, which keeps the parent context clean. The output is a written investigation doc with the root cause, relevant files, approach options and risks.

Plan behind a human approval gate. This is the highest-leverage place for a human: reviewing a plan is cheap, reviewing a wrong diff is expensive.

Implement with one agent. Code changes are deeply interdependent, and two agents editing related files produce conflicts and inconsistent assumptions. Fan out implementation only when the ticket really splits (backend, frontend, docs), and then with strict file ownership that never overlaps.

Verify with a fresh evaluator, never the implementer. An agent grading its own work is systematically lenient. Spawn fresh agents that get the ticket and the diff: one runs the tests, one reviews against conventions, one checks the acceptance criteria. Findings go back to the implementer for at most 2 or 3 rounds, then escalate to a human.

By ticket size: a small ticket gets a single agent plus a verify step, a medium ticket gets the full pipeline, and only truly parallel workstreams get fan-out implementation with strict file ownership.

7. Concerns that apply to every pattern

  • Guardrails: input and output validation, prompt injection defense, PII filtering.
  • Caching: prompt caching for repeated context, semantic caching for repeated queries.
  • Evals: automated test sets plus LLM as judge. Without evals, everything else is guesswork.
  • Fallbacks and retries: model or provider fallback chains for reliability.

Hard-won warnings for multi-agent systems

  1. A single agent with good tools beats multi-agent most of the time. Add agents only when one agent's context or focus clearly breaks down.
  2. Context isolation is the real reason for sub-agents. If you're not getting that benefit, skip the pattern.
  3. Every agent boundary loses information, so write explicit contracts for what goes in and what must come back.
  4. Cost scales linearly with agents; reliability doesn't. Two agents that are each right 90% of the time, chained, are right about 81% of the time.
