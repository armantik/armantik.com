I.2Basic

Anatomy of a request

Before your code runs, a request pays for a name lookup and handshakes, and each one costs round trips. Knowing where the time goes explains why CDNs, connection reuse and HTTP/3 exist.

Round trip time (RTT)
Time for a packet to reach the other side and come back. Distance sets the floor: light in fiber covers about 200 km per millisecond.
DNS
Turns a name like example.com into an IP address. Answers are cached by browsers, operating systems and resolvers for the record’s TTL.
TCP handshake
SYN, SYN-ACK, ACK: one round trip before any data can flow.
TLS handshake
Agrees on keys to encrypt the connection: two round trips with TLS 1.2, one with TLS 1.3.
Time to first byte (TTFB)
From starting the request until the first byte of the response arrives. Setup, one round trip and server work all count.
Connection reuse
Keeping a connection open (keep-alive, pooling) so later requests skip DNS and both handshakes.

I.3Basic

Latency, throughput and percentiles

Latency is how long one request takes; throughput is how many you finish per second. Averages hide the slow requests users actually feel, so serious systems are measured in percentiles.

Latency
Time for one operation, measured end to end. Usually reported in milliseconds.
Throughput
Work completed per unit of time: requests per second, messages per second, MB per second.
Bandwidth
The maximum rate a link can carry. Throughput is what you actually get through it.
Percentile
p99 = 250 ms means 99% of requests finished within 250 ms and 1 in 100 took longer. p50 is the median.
Tail latency
The slow end of the distribution, p99 and beyond. It grows in importance as one user action fans out into many calls.
Mean
The average. A few very slow requests drag it far above what a typical user sees, so it describes nobody.

I.4Basic

Availability and the nines

Availability is the share of time a system does its job. Each extra nine is ten times harder to reach, and every component you chain together brings its own failures.

Availability
Uptime as a share of total time, such as 99.9%. Measured over a window, often 30 days.
MTBF
Mean time between failures: how long things usually run before breaking.
MTTR
Mean time to recovery: how long it takes to get back up once broken.
Single point of failure
A component whose failure stops the whole system.
Redundancy
Extra copies of a component so one can fail without an outage.
SLI, SLO, SLA
What you measure, the target you set for it, and the contract you sign with customers.
Formula  availability = MTBF ÷ (MTBF + MTTR)
Example  fails once a month (720 h), 1 h to recover   → 720 ÷ 721 = 99.86%
Faster   same failures, recover in 6 minutes          → 720 ÷ 720.1 = 99.99%

Recovering faster buys nines as surely as failing less often, and it is usually cheaper: good alerts, quick rollbacks and automatic failover.

I.5Intermediate

Load, utilization and queueing

A server at 50% utilization feels fast; at 95% the same server feels broken. Queueing explains why, and Little’s law turns traffic into the number of requests in flight.

Arrival rate (λ)
How many requests arrive per second.
Service time (S)
How long one request takes when nothing else is waiting.
Utilization (ρ)
The share of time a resource is busy: arrival rate × service time, for one server.
Little’s law
Requests in the system = arrival rate × time each one spends there. L = λ × W, true for any stable system.
Saturation
Work arrives faster than it can be served; queues and latency grow without limit.
Headroom
Spare capacity kept free for spikes and failures, often 30 to 40% at peak.

I.6Basic

Data models and storage

Every database is built around one shape of data and a few access patterns. Pick the shape that matches how you read, and the rest of the design gets easier.

Transaction
A group of reads and writes that succeed or fail as one unit.
ACID
Atomic (all or nothing), consistent (rules hold), isolated (as if one at a time), durable (survives crashes).
Index
A sorted structure, usually a B-tree, that finds rows without scanning the table. Speeds reads, slows writes.
OLTP and OLAP
Many small transactional reads and writes, versus large analytical scans over history.
Schema
The declared structure of the data. Enforced on write in relational databases, interpreted on read in many NoSQL stores.
Write-ahead log
Changes are appended to a log before being applied, so a crash can be replayed. Replication and change data capture read the same log.

I.7Basic

    
Communication patterns

    
How two parties exchange messages decides latency, server load and what happens when one side is slow. Five patterns cover nearly every design.

  

  

    
Synchronous
The caller waits for the answer. Simple, but the caller is only as fast and available as whatever it calls.

    
Asynchronous
The caller hands off work, often through a queue, and moves on. Decouples the two sides at the cost of eventual results.

    
Pull and push
Pull: the client asks for news. Push: the server sends it when it happens.

    
Webhook
An HTTP callback: you give a service a URL and it calls you when an event happens.

    
RPC
Calling a function on another machine as if it were local, as gRPC does with typed contracts.

    
Fan-out
One request or event that triggers many downstream calls or messages.

I.8Basic

    
Units, sizes and transfer times

    
Most estimation mistakes are unit mistakes: bits for bytes, or a thousand for 1,024. These are the numbers worth knowing by heart.

  

  

    
Bit and byte
A byte is 8 bits. Network speeds are quoted in bits (Mbps), file sizes in bytes (MB), so divide by 8.

    
KB and KiB
KB is 1,000 bytes; KiB is 1,024. For estimates the 2.4% difference does not matter; for disk sizes it adds up.

    
Throughput in practice
Protocol overhead and congestion usually leave 70 to 90% of the link rate for your data.

II.1Basic

    
The 45 minute plan

    
A system design interview is a conversation about tradeoffs under a clock. The same five moves work for every prompt in this guide, and each case study in Part V follows them in order.

  


  

  
    
    
  1. 1
    Clarify requirements
    Agree on users, features, scale and what matters most. Leave with 3 to 5 functional and 3 to 5 non-functional requirements written down.
    “Read heavy or write heavy? Is a few seconds of staleness acceptable?”
    2. 
    
  2. 2
    Estimate
    QPS, peak QPS, storage and bandwidth, rounded hard. You want the order of magnitude that decides the design, not precision.
    “35K reads per second is more than one database should take, so we need a cache.”
    3. 
    
  3. 3
    High level design
    API, data model, and one diagram of the request path. Get the interviewer to agree before you add detail.
    “That’s the happy path end to end. Which part should we go deeper on?”
    4. 
    
  4. 4
    Deep dive
    Two or three hard parts: the hot path, the data that grows, the failure that hurts. Show options, pick one, and say what it costs.
    “Push fan-out breaks for celebrities, so I’d switch them to pull.”
    5. 
    
  5. 5
    Wrap up
    Recap, name the bottlenecks, what you would monitor, and what changes at 10× traffic.
    “At 10× the fan-out workers go first. I’d alert on queue lag.”
    6. 
  


  
Mistakes that cost the most

  
    
    
  • Drawing boxes before the requirements are agreed.
    • 
    
  • Naming a product instead of the property you need. Say “a durable, ordered, replayable log” first, then “Kafka”.
    • 
    
  • Presenting one option. Interviewers want the alternative you rejected and why.
    • 
    
  • Ignoring failure. For every box, know what happens when it dies or a call to it times out.
    • 
    
  • Designing for planet scale when the numbers say 50 requests per second.

    Design decisions come from ratios. Memory is about 160 times faster than a random SSD read, and a request across an ocean costs as much time as a million memory lookups.

      •

  Part IV
  
    Building blocks
    
  
    The six components that appear in nearly every design. Learn what each one buys you and what it breaks.
    

    


    
  
    
    
    IV.1Basic
    
    
    Load balancing
    
    
    A load balancer takes every request on one public address and forwards it to a healthy server behind it. It gives you horizontal scaling (add servers) and failover (stop routing to a server that fails its health check).
    
  
    
  
    
  
    
    
    
      
    Layer 4 or layer 7
    
      
    Layer 4 balancers route TCP or UDP connections by IP and port. Very fast and protocol agnostic, but blind to URLs and headers.
    
      
    Layer 7 balancers speak HTTP. They route /api and /images to different pools, terminate TLS and retry safe requests. Examples: NGINX, Envoy, HAProxy, AWS ALB.
    
    
    
    
    
      
    Keeping it reliable
    
      
    Health checks call an endpoint such as /healthz every few seconds and take failing servers out of rotation.
    
      
    The balancer must not become the new single point of failure. Run an active and standby pair that share a floating IP, or several balancers behind DNS.

    IV.2Basic
    
    
    Caching
    
    
    A cache keeps a copy of hot data in memory so most reads skip the slow path. It works because real traffic is skewed: a small share of keys receives most of the requests.
    
  
    
  
    
  
    Caches exist at every layer: the browser, the CDN, the API gateway, an application cache such as Redis or Memcached, and the database’s own buffer pool. In interviews “add a cache” usually means an application cache, and the follow up is always the same: how does data get in, and how does stale data get out?
    

  

  
    
    
    
      
    Eviction policies
    
      
      
        
    • LRU evicts the least recently used key. The default almost everywhere.
      • 
        
    • LFU evicts the least frequently used. Better when popularity is stable.
      • 
        
    • TTL expires keys after a fixed time. Your safety net against stale data.
      • 
      
    
    
    
    
    
      
    Failure modes to name
    
      
      
        
    • Stampede. A hot key expires and thousands of requests hit the database at once. Let one request refresh while others wait, and add random jitter to TTLs.
      • 
        
    • Hot key. One key overloads one cache node. Replicate it under suffixes (key#1 to key#8) or keep a small local cache per server.
      • 
        
    • Stale reads. Update the database first, then delete the cache key.
      •

    IV.3Intermediate
    
    
    Consistent hashing
    
    
    When data is spread over N servers, you need a rule that maps each key to a server. The obvious rule, hash(key) mod N, remaps almost every key when N changes. For a cache cluster that means a sudden flood of misses; for a database, a huge migration.
    
  
    
  
    
    
    
      
    The ring
    
      
    Hash servers and keys onto the same circle of values. A key belongs to the first server found moving clockwise. Adding a server only takes keys from one neighbor; removing one hands its keys to the next. On average only 1/N of the keys move.
    
    
    
    
    
      
    Virtual nodes
    
      
    With one position per server the arcs are uneven, so some servers own far more keys. Give each server many positions (virtual nodes) and the load evens out; when a server leaves, its keys spread across all the others. Used by Dynamo, Cassandra, Riak and most sharded caches.

    IV.4Intermediate
    
    
    CAP and consistency
    
    
    When a network partition splits a replicated system, each side must choose: refuse requests it cannot answer correctly (consistency) or answer with what it has (availability). Partitions happen in every real network, so the practical question is which one you give up while it lasts.
    
  
    
  
    
  
    
    
    
      
    Choose consistency (CP) when
    
      
    A wrong answer is worse than no answer: account balances, inventory reservations, leader election, unique usernames. Examples: ZooKeeper, etcd, Spanner, a single primary relational database.
    
    
    
    
    
      
    Choose availability (AP) when
    
      
    A slightly old answer is fine and downtime is not: shopping carts, like counts, feeds, DNS. Examples: Cassandra and DynamoDB in their default modes.
    
    
    
  
    
  
    PACELC adds the everyday case: even with no partition, waiting for replicas to confirm (consistency) costs latency. Most tuning happens here, not during rare partitions.

      IV.5Intermediate
      
    
      Queues and streams
      
    
      A queue sits between a producer and a consumer so neither waits for the other. It absorbs bursts, lets each side scale on its own, and keeps work safe when a consumer crashes.
      
  
      
  
      
  
      
    
      
      
      Two shapes
      
      
      Message queue (RabbitMQ, SQS): each message goes to one consumer and is deleted once acknowledged. Good for jobs.
      
      
      Log or stream (Kafka, Kinesis, Pulsar): messages are kept for days in ordered partitions. Many consumer groups read at their own offset and can replay history. Good for events that several systems need.
      
    
      
    
      
      
      Delivery guarantees
      
      
      At most once may lose messages. At least once may deliver duplicates and is the usual default. Exactly once in practice means at least once delivery plus an idempotent consumer that ignores message IDs it has already processed.
      
      
      Ordering holds only within a partition, so partition by the key whose order matters, such as order_id. After N failed attempts, park a message in a dead letter queue instead of blocking the partition.

      Rate limiting
      
    
      A rate limiter caps how many requests a client can make in a window. It protects services from abuse and from well meaning clients stuck in retry loops, and it keeps costs predictable.

      Notification system
      
    
      Many services, three channels, unreliable third party providers. The design is about keeping channels isolated from each other, retrying without spamming, and respecting what each user asked for.
      
  
      
  
      
  
      Interview prompt
      Design a system that sends push notifications, SMS and email on behalf of every team in the company.
      
  
      
    
      Functional requirements
      • Send through push (iOS, Android), SMS and email.
      • Respect per user preferences, opt-outs and quiet hours.
      • Immediate, scheduled and bulk campaign sends from templates.
      • Track sent, delivered and opened.
      
    
      Non-functional requirements
      • Urgent messages such as login codes arrive within seconds.
      • No lost notifications, and no duplicates the user can see.
      • A slow provider in one channel never delays the others.
      
  
      
  
      Estimates
      

      Daily volume  10M push + 1M SMS + 5M email       = 16M per day, ≈ 185/s
Campaign peak 10M pushes in 10 minutes           ≈ 17,000/s
Log storage   16M × 500 B × 365 days             ≈ 2.9 TB per year
      
  
      
    
      API
      

      POST /v1/notifications
{ "eventId": "evt_8812", "userId": 42,
  "template": "payment_succeeded",
  "params": { "amount": "€50" },
  "channels": ["push", "email"],
  "priority": "high" }
→ 202 Accepted { "notificationId": "ntf_19a" }
      
    
      Data model
      

      devices        user_id, token, platform

               enabled, quiet_hours
notifications  id PK, event_id UNIQUE,
               user_id, channel, status,
               sent_at, opened_at
      
  
      

  
      Deep dive: delivery you can trust
      
  
        
    
      • Persist first. Write the notification row, then enqueue it. If a worker crashes, a sweeper finds rows stuck in PENDING and re-enqueues them.
        • 
    
      • Deduplicate by event ID. The unique constraint on event_id means a service that publishes the same event twice still produces one notification.
        • 
    
      • One queue per channel, with priority lanes. Login codes and payment alerts never wait behind a ten million user marketing campaign.
        • 
    
      • Retry with exponential backoff and jitter, within each provider’s rate limits. After a fixed number of attempts, move the message to a dead letter queue and alert.
        • 
    
      • Close the loop. Providers report delivery through callbacks; the app reports opens. Both update the status row.
        • 
  
      
  
      
    
      ChannelProvider examplesWatch out for
      
    
      
      PushAPNs (Apple), FCM (Google)Device tokens go stale. Delete a token when the provider reports the app as unregistered.

      EmailAmazon SES, SendGridBounces and spam complaints damage your sender reputation. Marketing email needs an unsubscribe link.
      
          
  
      
  
      Deep dive: not annoying people
      
  
      Check preferences at send time, not when the message is queued, because a user may opt out in between. Cap marketing messages per user per day, hold non-urgent messages during quiet hours in the user’s own time zone, and bundle bursts into digests: “12 people liked your post” instead of twelve pings.
      

  
      
    
      What the interviewer probes next
      
    
      How do you send a campaign to 10M users without breaking anything?
      A scheduler expands the audience in batches of a few thousand and feeds the low priority lane. Workers throttle to each provider’s quota. Transactional messages use their own lane and workers, so they are unaffected.
      
    
      A login code must arrive fast. How?
      A dedicated high priority queue with reserved workers, a short expiry (a code that arrives after it expires is useless), and a fallback from push to SMS if no delivery receipt arrives within a few seconds.
      
    
      The same event is published twice. Does the user get two pushes?
      No. The second insert violates the unique event_id and is dropped. As a second guard, the app ignores notification IDs it has already shown.
      
    
      How do you know a notification was opened?
      The app reports opens with the notification ID; emails use a tracking pixel and wrapped links. Events stream into analytics and update the status row.

      Search autocomplete
      
    
      Every keystroke is a request, which makes this one of the busiest endpoints a company runs. The trick is to do the expensive ranking offline and make serving a plain memory lookup.
      
  
      
  
      
  
      Interview prompt
      Design the suggestions that appear under a search box as the user types.
      
  
      
    
      Functional requirements
      • Return the top 5 completions for a prefix, ranked by popularity.
      • Trending searches appear within about an hour.
      • Offensive and blocked terms never appear.
      
    
      Non-functional requirements
      • Under 100 ms end to end, so the server budget is about 20 ms.
      • Highly available; if suggestions fail, search still works.
      • Freshness of minutes to hours is fine.
      
  
      
  
      Estimates
      

      Requests     10M DAU × 10 searches × 20 keystrokes = 2B per day, ≈ 23,000/s
Peak         ≈ 2×                                   ≈ 50,000/s
Prefix index ≈ 1B prefixes × 5 IDs × 8 B         ≈ 40 GB plus keys, so shard it
      
  
      
    
      API
      

      GET /v1/suggest?q=tw&lang=en
→ 200 Cache-Control: max-age=3600
  { "suggestions": ["twitter", "twitch",
    "twilight", "twins", "tweetdeck"] }
      
    
      What each trie node stores
      

      prefix  top 5 completions, precomputed
t       twitter, twitch, tiktok, target, translate
tw      twitter, twitch, twilight, twins, tweetdeck
twi     twitch, twilight, twins, twitter, twine
      
  
      
  
      Storing the top five at every node is what makes serving fast: a lookup walks down as many nodes as the prefix has characters and returns the stored list, with no need to search the subtree below.
      

  
      Deep dive: where suggestions live
      
  
      
    
      ApproachServingUpdatingFits when
      
    
      
      Trie in memory, top 5 per node Common pickWalk the prefix, return the listRebuilt offline and swapped inThe classic interview answer

      Search engine completion suggesterIn memory automaton with fuzzy matchingNear real time indexingYou already run Elasticsearch or OpenSearch and need typo tolerance
      
          
  
      
  
      Deep dive: the data pipeline
      
  
      Search logs flow into a stream. A batch job counts queries over the last few weeks with older counts weighted less; a streaming job counts the last hour to catch trending terms. The scores are merged, a builder produces a new trie, writes it to object storage, and serving nodes load it and swap it in atomically. Reads never wait for writes.
      
  
      Deep dive: cutting the load
      
  
        
    
      • Debounce in the client: send only after a short pause in typing.
        • 
    
      • Cache responses in the browser, and at the CDN for short prefixes, which are the hottest and identical for everyone.
        • 
    
      • Shard by prefix range using a shard map balanced by traffic, because far more queries start with “s” than with “x”.
        • 
  
      

  
      
    
      What the interviewer probes next
      
    
      A harmful term starts trending. How do you remove it right now?
      Filter results against a blocklist at serving time, before returning them. The next rebuild removes the term from the trie itself.
      
    
      How would you personalize suggestions?
      Blend the global top results with the user’s own recent searches, kept on the device or in a small per user store, and merge them in the client or at the edge.
      
    
      How do you handle typos?
      Fuzzy matching by edit distance. It is much more expensive, so run it only when the exact prefix returns few results; completion suggesters in search engines support it directly.
      
    
      What about other languages?
      Build one trie per language or region, normalize Unicode, and for languages typed through an input method, such as Chinese pinyin, index the typed form as well as the final characters.
      
  
      

      



      
  
      
    
      V.6Intermediate
      
    
      Web crawler
      
    
      A crawler is a loop: take a URL, fetch it, extract its links, repeat. At a billion pages the hard parts are staying polite to every website, never fetching the same thing twice, and surviving the strange corners of the web.
      
  
      
  
      
  
      Interview prompt
      Design a web crawler that collects a billion pages a month for a search engine.
      
  
      
    
      Functional requirements
      • Start from seed URLs and follow links.
      • Store page content for indexing.
      • Recrawl pages according to how often they change.
      • Obey robots.txt.
      
    
      Non-functional requirements
      • Politeness: never overload any single website.
      • Scales to hundreds of fetcher machines.
      • Robust to broken HTML, slow servers and crawler traps.
      • Extensible to new content types such as PDFs.
      
  
      
  
      Estimates
      

      Fetch rate  1B pages ÷ 2.6M s per month         ≈ 385 pages/s, peak ≈ 800
Storage     1B × 500 KB                         = 500 TB per month, ≈ 30 PB in 5 years
URL seen    10B URLs in a Bloom filter at 1%    ≈ 12 GB of memory
      

  
      Deep dive: the URL frontier
      
  
  
      Deep dive: never twice
      
  
      
    
      
      
      Same URL
      
      
      Normalize first: lowercase the host, drop fragments, sort query parameters, strip tracking parameters. Then check a Bloom filter of URLs already seen. A false positive means a page is occasionally skipped, which is acceptable; it never causes a duplicate fetch.
      
    
      
    
      
      
      Same content
      
      
      Mirrors and session parameters serve identical pages under many URLs. A checksum of the content catches exact copies; SimHash catches near duplicates, such as the same article with a different ad block.
      
    
      
  
      
  
      
    
      TrapWhat happensDefense
      
    
      
      Endless calendars“Next month” links foreverMaximum depth and pages per host
      
      
      Session IDs in URLsEvery visit looks like a new pageStrip known parameters, content dedupe
      
      
      Generated link farmsPages that link to ever new pagesURL length limits, per host budgets
      
      
      Slow serversFetchers sit idle waitingTight timeouts; one host per back queue isolates it
      
          
  
      

  
      
    
      What the interviewer probes next
      
    
      How do you decide when to recrawl a page?
      Estimate each page’s change rate from past crawls: news front pages hourly, documentation monthly. Use conditional requests with If-Modified-Since or ETag, so unchanged pages return a 304 with no body.
      
    
      What about pages built with JavaScript?
      Send them to a separate render queue served by headless browsers. Rendering costs far more than fetching, so do it only when the static HTML lacks the content.
      
    
      How are hosts split across crawler machines?
      Hash the hostname to a machine with consistent hashing. One machine then owns all politeness state for a host, and adding machines moves only some hosts.
      
    
      DNS turns out to be the bottleneck. Why, and what helps?
      Each lookup can take tens to hundreds of milliseconds and many resolvers are single threaded. Run a caching resolver on every crawler machine and respect record TTLs.
      
  
      

      



      
  
      
    
      V.7Intermediate
      
    
      Nearby places
      
    
      A read heavy search problem with a twist: databases index one dimension well, and location has two. The design is mostly about the geospatial index.
      
  
      
  
      
  
      Interview prompt
      Design the backend for “restaurants near me” as in Yelp or Google Maps: given a location and a radius, return nearby businesses.
      
  
      
    
      Functional requirements
      • Search by location and radius: 0.5, 1, 2, 5 or 20 km.
      • View business details.
      • Owners add and update businesses; changes may appear the next day.
      
    
      Non-functional requirements
      • Low search latency.
      • Handles lunch and dinner peaks.
      • User locations are private and not stored longer than needed.
      
  
      
  
      Estimates
      

      Searches    100M DAU × 5 searches ÷ 86,400 s     ≈ 5,800 QPS, peak ≈ 15,000
Businesses  200M × 1 KB                           ≈ 200 GB
Geo index   200M × (6 B geohash + 8 B ID)         ≈ 3 GB, fits in memory
      
  
      Why a plain index fails
      

      SELECT id FROM business
WHERE lat BETWEEN 48.853 AND 48.863
  AND lng BETWEEN 2.284 AND 2.305;
      
  
      An index on latitude returns a thin strip around the whole planet, and one on longitude returns another. The database has to intersect two huge sets. What we need is a way to map two dimensions to one so that points close on the map stay close in the index.
      
  
      Geohash does this. Split the world in half by longitude and write 1 if the point is in the upper half, 0 if lower. Then split by latitude, then longitude again, alternating. Every 5 bits become one base32 character, and each extra character makes the cell 32 times smaller. Nearby points usually share a prefix, so “everything in this cell” becomes a prefix lookup.
      

  
      
    
      Explorer: encode a location
      
    
      
      
      
        
        
        
        
      
      
    
      
    
      
      
      
        
      
          
          
          
          
        
      
        
      Geohash
      
        
      
        
      Bits, 5 per character (blue longitude, red latitude)
      
        
      
        
      First splits
      
        
      
          
      AxisRangeMidpointBit
      
          
        
      
      
      
      
      
        
        
      
          
      Cell size here
      
          
      Suggested precision
      
        
      
        
      
      
      
    
      
  
      

  
      The boundary problem
      
  
      Two cafés across a street can sit in different cells with no shared prefix. So never search only the user’s cell: query the cell and its eight neighbors, compute exact distances for the candidates, drop those outside the radius and sort. If too few results come back, drop one character of precision and search again.
      

  
      
    
      IndexIdeaStrengthWeakness
      
    
      
      GeohashFixed grid, cell ID is a string prefixWorks in any database or Redis (GEOSEARCH); simple to shard and cacheFixed cell size regardless of density
      
      
      QuadtreeIn memory tree; split any cell holding more than K places into fourAdapts to density: small cells in Manhattan, huge ones in a desertBuilt at startup, harder to update live
      
      
      S2 or H3Hierarchical cells on a sphere (S2 squares on a Hilbert curve, Uber’s H3 hexagons)Covers any shape well; good for geofencesMore complex to explain and operate
      
          
  
      

  

  
      
    
      What the interviewer probes next
      
    
      What changes for moving objects, like ride share drivers?
      Locations update every few seconds, so it becomes write heavy. Keep driver positions in memory (Redis geo sets or an in memory grid keyed by cell) with short TTLs, and never write every update to the main database.
      
    
      Should we shard the geo index?
      Not by default. At 3 GB it fits in memory on every replica, and sharding by region creates hot shards in big cities. Replicate it and shard only the business table, by business ID.
      
    
      How do you cache searches when every user is at a different point?
      Cache by cell, not by coordinates: key is the geohash at the precision for the radius, value is the list of business IDs. Every user in the same cell shares the entry.

      Ticket booking
      
    
      Thousands of people want the same few seats in the same second. The design is about contention: exactly one buyer gets each seat, holds expire cleanly, and the on-sale spike never takes the site down.
      
  
      
  
      
  
      Interview prompt
      Design Ticketmaster: users find an event, choose seats and buy tickets.
      
  
      
    
      Functional requirements
      • Browse events and see a seat map with availability.
      • Hold seats for a few minutes during checkout.
      • Pay and receive tickets.
      • No seat is ever sold twice.
      
    
      Non-functional requirements
      • Strong consistency for seat state.
      • Survive on-sale spikes of millions of users.
      • Fair access; bots kept out.
      • Browsing may be a few seconds stale.
      
  
      
  
      Estimates
      

      Normal day  1M tickets per day                  ≈ 12 per second
Big on-sale 2M fans for 50,000 seats            = 40 fans per seat
Seat map    2M fans refreshing every 5 s         = 400,000 reads/s, so cache and push
      
  
      
    
      Data model
      

      events    event_id, venue_id, on_sale_at
seats     event_id, seat_id, section, price,
          status FREE | HELD | SOLD,
          held_by, hold_expires_at, version
bookings  booking_id, user_id, event_id,
          seat_ids, payment_id, status
      
    
      The one statement that matters
      

      UPDATE seats
SET status = 'HELD', held_by = :user,
    hold_expires_at = now() + interval '10 min'
WHERE event_id = :event AND seat_id = :seat
  AND (status = 'FREE' OR
      (status = 'HELD' AND hold_expires_at < now()));
/* 1 row changed: you hold it.
   0 rows: someone else does. */
      
  
      

  
      Deep dive: preventing double booking
      
  
      
    
      ApproachHowTradeoff
      
    
      
      Pessimistic lockSELECT … FOR UPDATE inside a transactionSimple; contenders queue on the row lock
      
      
      Optimistic lockRead version, then UPDATE … WHERE version = :vNo locks; under heavy contention most attempts fail and retry
      
      
      Conditional update Common pickOne UPDATE with the status check in WHEREAtomic, one round trip, no retry loop
      
      
      Redis hold with expirySET seat:A12 user NX PX 600000Fast holds off the database; the database must still enforce the final sale
      
          
  
      
  
      Deep dive: surviving the on-sale
      
  
        
    
      • Virtual waiting room. Fans get a place in line and a signed admission token; the booking service only accepts requests with a valid token and admits at the rate it can serve.
        • 
    
      • Seat map from cache, changes pushed. Serve the map from a cache refreshed every second or two and push seat changes over server-sent events. The hold step is authoritative, so a slightly stale map is harmless.
        • 
    
      • Split the hot event. One event cannot be sharded by event ID; partition its seats by section instead.
        • 
  
      

  
      
    
      What the interviewer probes next
      
    
      The hold expires while the fan is paying. Now what?
      Confirmation re-checks the hold. Extend it once when payment starts; if it was lost anyway and the charge succeeded, refund automatically and tell the fan clearly.
      
    
      Why not keep seat state in application memory?
      There are many application servers and their memory is not shared. One authority, the database or a single Redis key per seat, must arbitrate.
      
    
      How do you stop bots from buying everything?
      Verified fan presales, per account and per card limits, a challenge at waiting room entry, and device fingerprinting.
      
    
      How does this change for hotels or flights?
      Same core: conditional updates on inventory counts, holds with expiry and idempotent confirmation. Airlines also deliberately overbook, which is a business rule layered on top.

      Uploads are heavy but rare; views are light but constant and enormous. Most decisions trade compute at upload time for bandwidth at view time, and bandwidth is the bill that matters.
      
  
      
  
      
  
      Interview prompt
      Design YouTube: creators upload videos, and hundreds of millions of people watch them on any device and any connection.

      • Upload large files reliably.
      • Transcode into formats for every device and network.
      • Stream with fast start and few pauses.
      • Metadata, thumbnails, view counts.
      
    
      Non-functional requirements
      • Playback starts quickly and rarely rebuffers.
      • Highly available, and originals are never lost.
      • Cost efficient: egress dominates the bill.
      
  
      
  
      Estimates (assumptions)
      

      Uploads  1M videos per day × 300 MB          = 300 TB per day of originals
Views    1B views per day × 100 MB            = 100 PB per day
Egress   100 PB ÷ 86,400 s                    ≈ 1.2 TB/s, about 9 Tbps
Verdict  bandwidth dwarfs everything, so the CDN is the core of the design

      POST /v1/uploads                    → { uploadId, chunkUrls[] }

      Deep dive: the transcoding pipeline
      
  
  
      
    
      RenditionTypical bitrate, H.264Used for
      
    
      
      240p≈ 0.4 MbpsWeak mobile networks
      
      
      480p≈ 1.2 MbpsPhones on cellular

      Deep dive: adaptive bitrate streaming
      
  
      Each rendition is cut into segments of a few seconds and listed in a manifest (HLS or DASH). The player downloads segments one at a time, measures throughput and how much video is buffered, and picks the quality of the next segment accordingly. That is why video drops to a blurrier picture instead of freezing when the train enters a tunnel.
      
  
      Deep dive: spending to save
      
  
      Newer codecs such as VP9 and AV1 need noticeably less bandwidth for the same quality but cost far more to encode. Spend that compute on popular videos, where every saved byte is multiplied by millions of views; keep the long tail on cheaper encodes. Push popular videos to edge caches ahead of demand; Netflix goes further and places its own cache servers inside internet providers’ networks.

      How do you count billions of views?
      Players send events to a stream; a job aggregates them per video per minute and updates counters in batches. Show an approximate count live and reconcile the exact one later, deduplicating by session.
      
    
      What changes for live streaming?
      There is no time for a big transcoding graph. Ingest over RTMP or SRT, transcode a few renditions in real time, and use segments of one or two seconds (low latency HLS). The CDN still does the fan-out.
      
    
      How do you resume where the viewer stopped?
      The player reports its position every few seconds to a per user key value store, read on the next play.
      
    
      How do you detect copyrighted uploads?
      Fingerprint the audio and video during processing and compare against a reference database, then block, monetize or track according to the owner’s policy.

      • All copies converge to the same text.
      • No acknowledged keystroke is lost.

Servers    ≈ 10,000 active documents per server    ≈ 100+ collaboration servers

      Deep dive: OT or CRDT
      
  
      
    
      Operational transformation (OT)CRDT
      
    
      
      How it convergesA server orders operations and transforms each against concurrent ones it already appliedEvery character gets a unique ID; merges are commutative, so any order gives the same result

      ExamplesGoogle DocsYjs, Automerge, many local-first apps
      
          
  
      
  
      Deep dive: one document, one server
      
  
      Transformation needs a single ordering point, so every editor of a document must reach the same collaboration server. Route by doc_id with consistent hashing and a lookup service. That server holds the document in memory, assigns each operation the next version, appends it to the log, and broadcasts it. A client sends each operation with the version it was based on; if the server has moved on, it transforms the operation before applying it.
      
  
      Cursors and selections are presence data: broadcast a few times per second, never persisted.
      

  
      
    
      What the interviewer probes next
      
    
      The server for a document crashes.
      Another server claims the doc_id, loads the latest snapshot plus the operations after it, and clients reconnect. Each client resends unacknowledged operations with their base version and client operation ID, and the server transforms them and drops any it already applied.
      
    
      How does version history work?
      Replay operations from the nearest snapshot to reach any version. For the history panel, group operations into sessions by author and time.
      
    
      Why not just lock the paragraph being edited?
      It is simpler but feels broken: people expect to type anywhere. OT and CRDTs give lock-free editing.
      
    
      What about very large documents?
      Split them into blocks or pages, load lazily, and scope operations to blocks so a change in chapter 9 never touches chapter 1.
      
  
      

      


      
  
      
    
      V.13Advanced
      
    
      Distributed key value store
      
    
      The advanced classic, modeled on Amazon’s Dynamo paper. Every technique from Part IV shows up here, combined, and the interviewer will ask what each one costs.
      
  
      
  
      
  
      Interview prompt
      Design a key value store like Dynamo or Cassandra: put(key, value) and get(key) across hundreds of nodes, always writable.
      
  
      
    
      Functional requirements
      • put and get for values under 10 KB.
      • Tunable consistency per request.
      
    
      Non-functional requirements
      • Petabytes of data, horizontal scaling, no downtime to add nodes.
      • High availability: writes succeed even during failures.
      • Low latency at the 99th percentile.
      
  
      
  
      
    
      ProblemTechniqueWhat it gives you
      
    
      
      Data larger than one machineConsistent hashing with virtual nodesEven spread; adding a node moves only its share
      
      
      Node lossReplicate to the next N distinct nodes clockwiseCopies on separate machines, racks and zones
      
      
      Freshness against latencyQuorums N, R, WChoose per request
      
      
      Concurrent writes to one keyVector clocks or last write winsDetect conflicts, then resolve them
      
      
      Temporary failureSloppy quorum and hinted handoffWrites succeed while a replica is down
      
      
      Permanent failure, driftAnti-entropy with Merkle treesReplicas resync, moving only what differs

      Deep dive: conflicts and vector clocks
      
  
      With W below N, two clients can update the same key on different replicas at once. A vector clock is a list of [server, counter] pairs attached to each version. If one version’s counters are all greater or equal, it descends from the other and wins. If neither dominates, the writes were concurrent and the system keeps both for the client to merge.
      
  

  
      Deep dive: failures
      
  
      
    
      
      
      Detecting them
      
      
      Every node keeps a membership list with heartbeat counters and gossips it to a few random peers each second. If a node’s counter stops rising for a while, peers mark it down. News reaches every node in about log N rounds, with no single monitor to fail.
      
    
      
    
      
      
      Surviving them
      
      
      Hinted handoff: if a replica is down, the write goes to the next healthy node with a note naming the real owner, and is handed back when it returns. Merkle trees let two replicas compare hashes of key ranges and sync only the branches that differ.
      
    
      
  
      
  

  
      
    
      What the interviewer probes next
      
    
      Why not just use last write wins?
      It is simple but silently discards one of two concurrent writes, and clock skew between servers makes the choice arbitrary. Fine for caches and full overwrites; wrong for carts or counters where both updates should survive.
      
    
      How does a read find the latest version?
      The coordinator reads R replicas and returns the newest version, or all concurrent ones. Replicas that returned stale data are fixed in the background (read repair).
      
    
      How do you add a node with no downtime?
      The new node takes its virtual positions on the ring, streams the key ranges it now owns from their current owners, then starts serving. Only neighboring ranges move.
      
    
      How do you place replicas across data centers?
      Walk the ring but skip nodes in a rack or zone that already holds a copy, so N replicas land in N failure domains. Cassandra calls this a network topology strategy.
      
  
      

      



      
  
      
    
      V.14Advanced
      
    
      Payment system
      
    
      Low throughput, zero tolerance. Here the hard part is not scale but correctness across unreliable networks: never charge twice, never lose money, and prove it with a ledger.
      
  
      
  
      
  
      Interview prompt
      Design the payment backend for a marketplace: customers pay, sellers get paid out, and the books always balance.
      
  
      
    
      Functional requirements
      • Pay-in: charge the customer through a payment service provider (PSP) such as Stripe or Adyen.
      • Pay-out to sellers, refunds.
      • Reconciliation with the PSP.
      
    
      Non-functional requirements
      • Correctness first: no double charges, no lost payments.
      • Auditable history of every movement of money.
      • Card data never stored by us (PCI DSS scope).
      
  
      
  
      Estimates
      

      Payments  1M per day ÷ 86,400 s     ≈ 12 per second
Peak      Black Friday, 10×         ≈ 120 per second
Verdict   one database handles this; spend the design effort on correctness
      

  
  
      The flow
      
  
        
    
      1. Checkout sends a payment request with an idempotency key, for example the order ID. The payment service stores the order as NOT_STARTED.
        2. 
    
      2. The executor calls the PSP. Card details never touch our servers: the PSP’s hosted page or SDK turns them into a token.
        3. 
    
      3. The PSP answers, or calls our webhook later, and the order moves to SUCCESS or FAILED.
        4. 
    
      4. On success, the wallet balance and ledger entries are written in one transaction, or through the outbox pattern if they live in different services.
        5. 
    
      5. Nightly, reconciliation matches the PSP settlement file line by line against the ledger and flags every mismatch.
        6. 
  
      

  
      
    
      Simulator: a timeout, a retry, and the idempotency key
      
    
      
      
      
    
      
    
        
    
        
      
        Charges at the PSP
        Charges
        0
        Buyer charged
        €0
        
      
        Idempotency table
        KeyStored result
        Empty
        
    
        
    
        A timeout does not mean the charge failed. The server may have finished the work and only the response was lost. Retrying is necessary (at least once), and the idempotency key makes the retry harmless (at most once). Together they give the exactly once effect.
        
  
        

  
        Deep dive: the double entry ledger
        
  
        
    
        EntryAccountDebitCredit
        
    
      
        1Buyer, card via PSP€50.00
        
      
        2Seller payable€45.00
        
      
        3Platform fee revenue€5.00
        
      
        Total€50.00€50.00
        
            
  
        
  
        Every transaction debits and credits the same total, so the sum of all entries is always zero. Entries are append only: a refund is a new pair of entries, never an edit. If the books ever fail to balance, you can trace exactly which transaction broke them.
        
  
        Deep dive: retries and distributed steps
        
  
          
    
        • Retry with exponential backoff and jitter: about 1, 2, 4, 8 seconds, each randomized so thousands of clients do not retry in lockstep. Then stop and alert.
          • 
    
        • Check before retrying an unknown outcome: query the PSP for the payment’s status using the same key.
          • 
    
        • Outbox pattern: write the state change and the event to publish in the same database transaction; a relay publishes the event afterwards. No “saved but never announced” gaps.
          • 
    
        • Saga for multi-step flows: each step has a compensating action (a refund undoes a charge) instead of a distributed lock.
          • 
    
        • Store money as integers in minor units (cents) with a currency code. Floating point cannot represent 0.10 exactly.
          • 
  
        
  
        
    
        What the interviewer probes next
        
    
        The PSP is down. What do customers see?
        Route to a secondary PSP where contracts allow, protected by a circuit breaker so failing calls stop quickly. If none is available, fail fast with a clear error; never leave a payment in an unknown state without a follow up job to resolve it.
        
    
        How are sellers paid out?
        A daily batch sends pay-outs through the PSP or a bank, with the same idempotency keys and ledger entries. Funds are held for a period so refunds and chargebacks can be covered.
        
    
        What does reconciliation do with a mismatch?
        Classify it. Known patterns (a delayed webhook) are fixed automatically; unknown ones go to a finance queue for manual review. The point is that no discrepancy goes unnoticed for more than a day.
        
    
        What is a chargeback, and how does the ledger handle it?
        The customer disputes the charge with their bank, which pulls the money back. The ledger records reversing entries against the seller’s balance, which may go negative until the next pay-out settles it.
