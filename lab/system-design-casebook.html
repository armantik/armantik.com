I.2Basic

Anatomy of a request

Before your code runs, a request pays for a name lookup and handshakes, and each one costs round trips. Knowing where the time goes explains why CDNs, connection reuse and HTTP/3 exist.

Round trip time (RTT)
Time for a packet to reach the other side and come back. Distance sets the floor: light in fiber covers about 200 km per millisecond.
DNS
Turns a name like example.com into an IP address. Answers are cached by browsers, operating systems and resolvers for the record’s TTL.
TCP handshake
SYN, SYN-ACK, ACK: one round trip before any data can flow.
TLS handshake
Agrees on keys to encrypt the connection: two round trips with TLS 1.2, one with TLS 1.3.
Time to first byte (TTFB)
From starting the request until the first byte of the response arrives. Setup, one round trip and server work all count.
Connection reuse
Keeping a connection open (keep-alive, pooling) so later requests skip DNS and both handshakes.

I.3Basic

Latency, throughput and percentiles

Latency is how long one request takes; throughput is how many you finish per second. Averages hide the slow requests users actually feel, so serious systems are measured in percentiles.

Latency
Time for one operation, measured end to end. Usually reported in milliseconds.
Throughput
Work completed per unit of time: requests per second, messages per second, MB per second.
Bandwidth
The maximum rate a link can carry. Throughput is what you actually get through it.
Percentile
p99 = 250 ms means 99% of requests finished within 250 ms and 1 in 100 took longer. p50 is the median.
Tail latency
The slow end of the distribution, p99 and beyond. It grows in importance as one user action fans out into many calls.
Mean
The average. A few very slow requests drag it far above what a typical user sees, so it describes nobody.

I.4Basic

Availability and the nines

Availability is the share of time a system does its job. Each extra nine is ten times harder to reach, and every component you chain together brings its own failures.

Availability
Uptime as a share of total time, such as 99.9%. Measured over a window, often 30 days.
MTBF
Mean time between failures: how long things usually run before breaking.
MTTR
Mean time to recovery: how long it takes to get back up once broken.
Single point of failure
A component whose failure stops the whole system.
Redundancy
Extra copies of a component so one can fail without an outage.
SLI, SLO, SLA
What you measure, the target you set for it, and the contract you sign with customers.
Formula  availability = MTBF ÷ (MTBF + MTTR)
Example  fails once a month (720 h), 1 h to recover   → 720 ÷ 721 = 99.86%
Faster   same failures, recover in 6 minutes          → 720 ÷ 720.1 = 99.99%

Recovering faster buys nines as surely as failing less often, and it is usually cheaper: good alerts, quick rollbacks and automatic failover.

I.5Intermediate

Load, utilization and queueing

A server at 50% utilization feels fast; at 95% the same server feels broken. Queueing explains why, and Little’s law turns traffic into the number of requests in flight.

Arrival rate (λ)
How many requests arrive per second.
Service time (S)
How long one request takes when nothing else is waiting.
Utilization (ρ)
The share of time a resource is busy: arrival rate × service time, for one server.
Little’s law
Requests in the system = arrival rate × time each one spends there. L = λ × W, true for any stable system.
Saturation
Work arrives faster than it can be served; queues and latency grow without limit.
Headroom
Spare capacity kept free for spikes and failures, often 30 to 40% at peak.

I.6Basic

Data models and storage

Every database is built around one shape of data and a few access patterns. Pick the shape that matches how you read, and the rest of the design gets easier.

Transaction
A group of reads and writes that succeed or fail as one unit.
ACID
Atomic (all or nothing), consistent (rules hold), isolated (as if one at a time), durable (survives crashes).
Index
A sorted structure, usually a B-tree, that finds rows without scanning the table. Speeds reads, slows writes.
OLTP and OLAP
Many small transactional reads and writes, versus large analytical scans over history.
Schema
The declared structure of the data. Enforced on write in relational databases, interpreted on read in many NoSQL stores.
Write-ahead log
Changes are appended to a log before being applied, so a crash can be replayed. Replication and change data capture read the same log.

I.7Basic

    
Communication patterns

    
How two parties exchange messages decides latency, server load and what happens when one side is slow. Five patterns cover nearly every design.

  

  

    
Synchronous
The caller waits for the answer. Simple, but the caller is only as fast and available as whatever it calls.

    
Asynchronous
The caller hands off work, often through a queue, and moves on. Decouples the two sides at the cost of eventual results.

    
Pull and push
Pull: the client asks for news. Push: the server sends it when it happens.

    
Webhook
An HTTP callback: you give a service a URL and it calls you when an event happens.

    
RPC
Calling a function on another machine as if it were local, as gRPC does with typed contracts.

    
Fan-out
One request or event that triggers many downstream calls or messages.

I.8Basic

    
Units, sizes and transfer times

    
Most estimation mistakes are unit mistakes: bits for bytes, or a thousand for 1,024. These are the numbers worth knowing by heart.

  

  

    
Bit and byte
A byte is 8 bits. Network speeds are quoted in bits (Mbps), file sizes in bytes (MB), so divide by 8.

    
KB and KiB
KB is 1,000 bytes; KiB is 1,024. For estimates the 2.4% difference does not matter; for disk sizes it adds up.

    
Throughput in practice
Protocol overhead and congestion usually leave 70 to 90% of the link rate for your data.

II.1Basic

    
The 45 minute plan

    
A system design interview is a conversation about tradeoffs under a clock. The same five moves work for every prompt in this guide, and each case study in Part V follows them in order.

  


  

  
    
    
  1. 1
    Clarify requirements
    Agree on users, features, scale and what matters most. Leave with 3 to 5 functional and 3 to 5 non-functional requirements written down.
    “Read heavy or write heavy? Is a few seconds of staleness acceptable?”
    2. 
    
  2. 2
    Estimate
    QPS, peak QPS, storage and bandwidth, rounded hard. You want the order of magnitude that decides the design, not precision.
    “35K reads per second is more than one database should take, so we need a cache.”
    3. 
    
  3. 3
    High level design
    API, data model, and one diagram of the request path. Get the interviewer to agree before you add detail.
    “That’s the happy path end to end. Which part should we go deeper on?”
    4. 
    
  4. 4
    Deep dive
    Two or three hard parts: the hot path, the data that grows, the failure that hurts. Show options, pick one, and say what it costs.
    “Push fan-out breaks for celebrities, so I’d switch them to pull.”
    5. 
    
  5. 5
    Wrap up
    Recap, name the bottlenecks, what you would monitor, and what changes at 10× traffic.
    “At 10× the fan-out workers go first. I’d alert on queue lag.”
    6. 
  


  
Mistakes that cost the most

  
    
    
  • Drawing boxes before the requirements are agreed.
    • 
    
  • Naming a product instead of the property you need. Say “a durable, ordered, replayable log” first, then “Kafka”.
    • 
    
  • Presenting one option. Interviewers want the alternative you rejected and why.
    • 
    
  • Ignoring failure. For every box, know what happens when it dies or a call to it times out.
    • 
    
  • Designing for planet scale when the numbers say 50 requests per second.

    Design decisions come from ratios. Memory is about 160 times faster than a random SSD read, and a request across an ocean costs as much time as a million memory lookups.

  Part IV
  
    Building blocks
    
  
    The six components that appear in nearly every design. Learn what each one buys you and what it breaks.
    

    


    
  
    
    
    IV.1Basic
    
    
    Load balancing
    
    
    A load balancer takes every request on one public address and forwards it to a healthy server behind it. It gives you horizontal scaling (add servers) and failover (stop routing to a server that fails its health check).
    
  
    
  
    
  
    
    
    
      
    Layer 4 or layer 7
    
      
    Layer 4 balancers route TCP or UDP connections by IP and port. Very fast and protocol agnostic, but blind to URLs and headers.
    
      
    Layer 7 balancers speak HTTP. They route /api and /images to different pools, terminate TLS and retry safe requests. Examples: NGINX, Envoy, HAProxy, AWS ALB.
    
    
    
    
    
      
    Keeping it reliable
    
      
    Health checks call an endpoint such as /healthz every few seconds and take failing servers out of rotation.
    
      
    The balancer must not become the new single point of failure. Run an active and standby pair that share a floating IP, or several balancers behind DNS.

    IV.2Basic
    
    
    Caching
    
    
    A cache keeps a copy of hot data in memory so most reads skip the slow path. It works because real traffic is skewed: a small share of keys receives most of the requests.
    
  
    
  
    
  
    Caches exist at every layer: the browser, the CDN, the API gateway, an application cache such as Redis or Memcached, and the database’s own buffer pool. In interviews “add a cache” usually means an application cache, and the follow up is always the same: how does data get in, and how does stale data get out?
    

  

  
    
    
    
      
    Eviction policies
    
      
      
        
    • LRU evicts the least recently used key. The default almost everywhere.
      • 
        
    • LFU evicts the least frequently used. Better when popularity is stable.
      • 
        
    • TTL expires keys after a fixed time. Your safety net against stale data.
      • 
      
    
    
    
    
    
      
    Failure modes to name
    
      
      
        
    • Stampede. A hot key expires and thousands of requests hit the database at once. Let one request refresh while others wait, and add random jitter to TTLs.
      • 
        
    • Hot key. One key overloads one cache node. Replicate it under suffixes (key#1 to key#8) or keep a small local cache per server.
      • 
        
    • Stale reads. Update the database first, then delete the cache key.
      •

    IV.3Intermediate
    
    
    Consistent hashing
    
    
    When data is spread over N servers, you need a rule that maps each key to a server. The obvious rule, hash(key) mod N, remaps almost every key when N changes. For a cache cluster that means a sudden flood of misses; for a database, a huge migration.
    
  
    
  
    
    
    
      
    The ring
    
      
    Hash servers and keys onto the same circle of values. A key belongs to the first server found moving clockwise. Adding a server only takes keys from one neighbor; removing one hands its keys to the next. On average only 1/N of the keys move.
    
    
    
    
    
      
    Virtual nodes
    
      
    With one position per server the arcs are uneven, so some servers own far more keys. Give each server many positions (virtual nodes) and the load evens out; when a server leaves, its keys spread across all the others. Used by Dynamo, Cassandra, Riak and most sharded caches.

    IV.4Intermediate
    
    
    CAP and consistency
    
    
    When a network partition splits a replicated system, each side must choose: refuse requests it cannot answer correctly (consistency) or answer with what it has (availability). Partitions happen in every real network, so the practical question is which one you give up while it lasts.
    
  
    
  
    
  
    
    
    
      
    Choose consistency (CP) when
    
      
    A wrong answer is worse than no answer: account balances, inventory reservations, leader election, unique usernames. Examples: ZooKeeper, etcd, Spanner, a single primary relational database.
    
    
    
    
    
      
    Choose availability (AP) when
    
      
    A slightly old answer is fine and downtime is not: shopping carts, like counts, feeds, DNS. Examples: Cassandra and DynamoDB in their default modes.
    
    
    
  
    
  
    PACELC adds the everyday case: even with no partition, waiting for replicas to confirm (consistency) costs latency. Most tuning happens here, not during rare partitions.

      IV.5Intermediate
      
    
      Queues and streams
      
    
      A queue sits between a producer and a consumer so neither waits for the other. It absorbs bursts, lets each side scale on its own, and keeps work safe when a consumer crashes.
      
  
      
  
      
  
      
    
      
      
      Two shapes
      
      
      Message queue (RabbitMQ, SQS): each message goes to one consumer and is deleted once acknowledged. Good for jobs.
      
      
      Log or stream (Kafka, Kinesis, Pulsar): messages are kept for days in ordered partitions. Many consumer groups read at their own offset and can replay history. Good for events that several systems need.
      
    
      
    
      
      
      Delivery guarantees
      
      
      At most once may lose messages. At least once may deliver duplicates and is the usual default. Exactly once in practice means at least once delivery plus an idempotent consumer that ignores message IDs it has already processed.
      
      
      Ordering holds only within a partition, so partition by the key whose order matters, such as order_id. After N failed attempts, park a message in a dead letter queue instead of blocking the partition.

      A rate limiter caps how many requests a client can make in a window. It protects services from abuse and from well meaning clients stuck in retry loops, and it keeps costs predictable.

      Put the limiter in the API gateway or as middleware, keyed by user ID, API key or IP. Counters live in Redis so every gateway node sees the same numbers; wrap check and decrement in a Lua script (or use INCR with EXPIRE) so two nodes cannot both spend the last token. Rejected calls get 429 Too Many Requests with a Retry-After header, and well behaved clients back off exponentially.

        Deep dive: 301 or 302
        
  
        A 301 Moved Permanently is cached by the browser, so repeat visits never reach you. Less load, but you lose click analytics and cannot change or expire the link for that visitor. A 302 Found sends every click through your servers: more load, complete analytics. Most commercial shorteners use 302 because analytics is the product.
        
  
        Deep dive: scaling reads
        
  
        Redirects outnumber writes 100 to 1, and clicks concentrate on recent and viral links. Cache code → long URL in Redis with LRU eviction. If the hottest 20% of a month’s links take most of the clicks, that is 20M × 500 B = 10 GB, which fits in one Redis node. Add read replicas behind the cache, and for extreme traffic answer redirects at the CDN edge.
        

  
        
    
        What the interviewer probes next
        
    
        How do custom aliases work?
        Same table, same unique key. Check availability on create and reserve words like api and login. To keep aliases from colliding with generated codes, generated codes are always exactly 7 characters and aliases must be another length, or both go through the same uniqueness check.
        
    
        How do expired links get cleaned up?
        Lazily on read (return 410 Gone when expired) plus a low priority job that deletes expired rows in batches. Never recycle codes: an old link printed in a book would suddenly point at a stranger’s page.
        
    
        How do you count clicks without slowing redirects?
        Redirect first, then publish a click event to a queue such as Kafka. Stream processors aggregate counts per link per minute into an analytics store. The redirect never waits on analytics.
        
    
        How do you stop abuse?
        Rate limit creation per user and IP, check new URLs against malware and phishing lists such as Google Safe Browsing, and require an account for high volume.

        Feeds store IDs only. Hydration reads the current post, and deleted posts are filtered out at read time, so nothing needs to be rewritten across millions of feeds.
        
    
        How do media uploads fit in?
        Clients upload directly to object storage with a pre-signed URL, a worker creates thumbnails, and the CDN serves them. Posts keep only media IDs.

        Chat system
        
    
        Chat introduces stateful servers: millions of open connections that must find each other. The design turns on how a message travels from one socket to another, and what happens when the other side is offline.
        
  
        
  
        
  
        Interview prompt
        Design a chat app like WhatsApp or Messenger: one to one and small group chats, online status, and sync across devices.
        
  
        
    
        Functional requirements
        • One to one and group chats of up to 100 members.
        • Delivery and read receipts, online presence.
        • Offline users get push notifications and catch up on reconnect.
        • History syncs across a user’s devices.
        
    
        Non-functional requirements
        • Low delivery latency.
        • Messages ordered within a conversation.

        Deep dive: storage, presence, groups
        
  
        
    
        
      
        Message store
        
      
        Chat is write heavy and reads are mostly recent. A wide column store (Cassandra, HBase, ScyllaDB) partitioned by conversation_id and sorted by message_id serves “latest 50 messages” from one partition. Discord runs this model on ScyllaDB, and Facebook Messenger ran it on HBase for years.
        
      
        Multi-device sync
        
      
        Each device keeps a cursor: the largest message ID it has. On reconnect it asks for everything after that ID, which also covers offline delivery.
        
    
        
    
        
      
        Presence
        
      
        Clients send a heartbeat every 5 seconds. A user is marked offline only after 30 seconds of silence, so a train through a tunnel does not flicker their status. Changes are published to friends over pub/sub; in large groups, presence is fetched only when someone opens the member list.
        
      
        Groups
        
      
        Small groups copy each message into every member’s inbox queue. Large channels store once and let members pull, like celebrities in the news feed.
        
    
        
  
        

  
        
    
        What the interviewer probes next
        
    
        A chat server crashes. What happens to its users?
        Their sockets drop, and clients reconnect with backoff and jitter; service discovery (ZooKeeper, etcd) hands them another server. Messages were persisted before delivery, and clients resend anything unacknowledged with the same client message ID, which the server deduplicates.
        
    
        Two people in a group send at the same moment. Who comes first?
        Whoever the server assigns the lower ID. Using one ID source per conversation gives every member the same order; device timestamps are only for display.
        
    
        How does end to end encryption change the design?
        Keys live only on devices (the Signal protocol), so servers store and forward ciphertext. Server side search and message previews in push notifications no longer work unless the device decrypts them locally.
        
    
        How do you deploy without dropping 10M connections?
        Drain servers one at a time: stop accepting new sockets, ask connected clients to reconnect gradually, then restart. The load balancer must support long lived connections and not cut them on a fixed timeout.

        Why a plain index fails
        

        SELECT id FROM business
WHERE lat BETWEEN 48.853 AND 48.863
  AND lng BETWEEN 2.284 AND 2.305;

Every 5 bits become one base32 character, and each extra character makes the cell 32 times smaller. Nearby points usually share a prefix, so “everything in this cell” becomes a prefix lookup.

        Deep dive: conflicts and vector clocks
        
  
        With W below N, two clients can update the same key on different replicas at once. A vector clock is a list of [server, counter] pairs attached to each version. If one version’s counters are all greater or equal, it descends from the other and wins. If neither dominates, the writes were concurrent and the system keeps both for the client to merge.
        
  

  
        Deep dive: failures
        
  
        
    
        
      
        Detecting them
        
      
        Every node keeps a membership list with heartbeat counters and gossips it to a few random peers each second. If a node’s counter stops rising for a while, peers mark it down. News reaches every node in about log N rounds, with no single monitor to fail.
        
    
        
    
        
      
        Surviving them
        
      
        Hinted handoff: if a replica is down, the write goes to the next healthy node with a note naming the real owner, and is handed back when it returns. Merkle trees let two replicas compare hashes of key ranges and sync only the branches that differ.
        
    
        
  
        
  

  
        
    
        What the interviewer probes next
        
    
        Why not just use last write wins?
        It is simple but silently discards one of two concurrent writes, and clock skew between servers makes the choice arbitrary. Fine for caches and full overwrites; wrong for carts or counters where both updates should survive.
        
    
        How does a read find the latest version?
        The coordinator reads R replicas and returns the newest version, or all concurrent ones. Replicas that returned stale data are fixed in the background (read repair).
        
    
        How do you add a node with no downtime?
        The new node takes its virtual positions on the ring, streams the key ranges it now owns from their current owners, then starts serving. Only neighboring ranges move.
        
    
        How do you place replicas across data centers?
        Walk the ring but skip nodes in a rack or zone that already holds a copy, so N replicas land in N failure domains. Cassandra calls this a network topology strategy.
        
  
        

        



        
  
        
    
        V.14Advanced
        
    
        Payment system
        
    
        Low throughput, zero tolerance. Here the hard part is not scale but correctness across unreliable networks: never charge twice, never lose money, and prove it with a ledger.
        
  
        
  
        
  
        Interview prompt
        Design the payment backend for a marketplace: customers pay, sellers get paid out, and the books always balance.
        
  
        
    
        Functional requirements
        • Pay-in: charge the customer through a payment service provider (PSP) such as Stripe or Adyen.
        • Pay-out to sellers, refunds.
        • Reconciliation with the PSP.
        
    
        Non-functional requirements
        • Correctness first: no double charges, no lost payments.
        • Auditable history of every movement of money.
        • Card data never stored by us (PCI DSS scope).

          3. 
    
        3. The PSP answers, or calls our webhook later, and the order moves to SUCCESS or FAILED.
          4. 
    
        4. On success, the wallet balance and ledger entries are written in one transaction, or through the outbox pattern if they live in different services.
          5.

          Deep dive: the double entry ledger
          
  
          
    
          EntryAccountDebitCredit
          
    
      
          1Buyer, card via PSP€50.00

          Every transaction debits and credits the same total, so the sum of all entries is always zero. Entries are append only: a refund is a new pair of entries, never an edit. If the books ever fail to balance, you can trace exactly which transaction broke them.
          
  
          Deep dive: retries and distributed steps
          
  
            
    
          • Retry with exponential backoff and jitter: about 1, 2, 4, 8 seconds, each randomized so thousands of clients do not retry in lockstep. Then stop and alert.
            • 
    
          • Check before retrying an unknown outcome: query the PSP for the payment’s status using the same key.
            • 
    
          • Outbox pattern: write the state change and the event to publish in the same database transaction; a relay publishes the event afterwards. No “saved but never announced” gaps.
            • 
    
          • Saga for multi-step flows: each step has a compensating action (a refund undoes a charge) instead of a distributed lock.
            • 
    
          • Store money as integers in minor units (cents) with a currency code. Floating point cannot represent 0.10 exactly.

          What the interviewer probes next
          
    
          The PSP is down. What do customers see?
          Route to a secondary PSP where contracts allow, protected by a circuit breaker so failing calls stop quickly. If none is available, fail fast with a clear error; never leave a payment in an unknown state without a follow up job to resolve it.
          
    
          How are sellers paid out?
          A daily batch sends pay-outs through the PSP or a bank, with the same idempotency keys and ledger entries. Funds are held for a period so refunds and chargebacks can be covered.
          
    
          What does reconciliation do with a mismatch?
          Classify it. Known patterns (a delayed webhook) are fixed automatically; unknown ones go to a finance queue for manual review. The point is that no discrepancy goes unnoticed for more than a day.
          
    
          What is a chargeback, and how does the ledger handle it?
          The customer disputes the charge with their bank, which pulls the money back. The ledger records reversing entries against the seller’s balance, which may go negative until the next pay-out settles it.
